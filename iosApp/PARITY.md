## B-BR-IOS-I18N / BUC-IOS-I18N — Language and regional formats

- The app follows the operating system's preferred app language. English is the development language. The available languages match Android: English, Brazilian Portuguese, Spanish, German, French, Japanese, Russian and Simplified Chinese.

## B-BR-IOS-COMMUNITY / BUC-IOS-COMMUNITY — Community and forum

- Public forum and station-feedback lists use opaque cursors and preserve server order. A refresh replaces the loaded page and cursor together. The forum feed sends Android's server filters: category, publication type, state, a seven-digit IBGE municipality inside that state, the forum fuel code and a station UUID. Forum text search covers loaded posts. The app labels this scope. Threads show the server's parent and depth, with ranked top-level forum comments and on-demand replies. A newer filter, account, origin, refresh or navigation entry wins over an earlier response.
- Observation actions require the server's contribution reference and decision sequence. Confirmation and dispute use device proof and the same submission id on retry. Helpfulness accepts HELPFUL and NOT_HELPFUL, can be removed, and uses its own tally. The public tally omits the owner's choice. Ratings are separate, use integer stars from one to five, and keep the mean absent when there are no ratings.
- Station feedback writes use the existing session envelope. Comment edits carry the last server revision and normalized text of at most 280 Unicode scalars. Feedback replies have one level. The app exposes edit and removal for owner receipts it can verify. Feedback creation has no server operation id, so a creation whose outcome is unknown is never resent automatically. The outbox keeps it as "might have reached the server" until the user reloads and chooses to send it again. Failures that prove nothing was applied (no connection before sending, 401, 408, 429 or another 4xx) keep their usual handling.
- Forum edit, removal, reaction and owner reads use the account session and bound device proof. Edits and removals use the owner revision. Topic owners edit the category, title, text, region and fuel and keep the station link and public alias. An edited comment or topic returns to moderation, and the thread reloads after a comment edit. Forum reactions are one LIKE, DISLIKE or NONE per target with authoritative counts and a private owner read. Each command keeps its operation id when retried.
- Reports follow their specific forum, station-comment or user contract. The app names users through a public content reference. Server-side blocks are private to their owner. The app filters topics, comments and reply previews through the signed hidden-content subset, allows up to five seconds for the check, and rechecks after a block changes. Logout, deletion and origin changes clear the private UI state.

## B-BR-IOS-ID / BUC-IOS-ID — Device identity and signed community writes

- Each signed request uses the backend profile: SHA-512 over the covered base, raw r||s P-256 signature as unpadded base64url, the canonical authority of the selected origin, and one fresh SIGN challenge. The content lines cover the exact body bytes. XCTest replays the Go identity vectors.
- A REGISTER challenge registers the device contributor once per process. With a live account session, the contributor is bound with `anpfuel-bind.v1` signed over SHA-256. The Keychain stores the contributor and key ids without iCloud synchronization. Android does not rotate keys, so iOS has no rotation flow.
- Sign in with Apple requests no scopes. Apple receives the SHA-256 hex of a random raw nonce. The backend receives the raw nonce, the identity token and the optional authorization code. Any login then registers and binds the device key.
- A free key account needs a public name and a recovery email proven with a six-digit code. The app requests the code with its purpose and resolved language, then calls `/v1/accounts/keys/signup`. Before it requests a code or saves a name, it applies the account API name rule, tested against `contracts/testdata/account/public-names-v1.tsv`. The key is shown once and saved with the session in the Keychain backup, and the device key is bound as after any login. If storage fails, the key stays on screen and signs in when the person continues.
- Key recovery proves the recovery email through `/v1/accounts/recovery`, replaces the Keychain backup and signs in. The previous key and other sessions stop working. The account sheet shows the public name and the masked recovery address, edits the name, and adds or changes the address. A change needs a fresh sign-in with the key or, for an Apple-linked account, with Apple. That proof never switches accounts.
- Passwordless email login has retired. The app no longer offers it or the legacy username sign-up. A 410 `account.email-login-retired` reply shows a message pointing to Apple or the account key. Code reuse, a linked address, an unknown recovery address, a reserved name and the 429 account budgets each have their own message.
- `/v1/accounts/providers/link-native` accepts only Google, which Android links. iOS has no Google sign-in, so it links no provider. Apple accounts sign in with Apple directly.
- Price observations are device-signed and may be anonymous. Station comments and votes need the account session. Forum topics and comments need the session plus the bound device proof. One client id per write serves as the idempotency key or forum operation id.
- An evidence photo needs a `photo-capture-community-v2` grant for the same station and a camera capture inside its two-minute window. Gallery photos only feed local OCR. A lapsed grant or a photo older than 24 hours expires without upload. Pix has no backend condition and is refused locally. The community API receives no device location.
- Outbox items are draft (waiting for sign-in), pending, accepted (with the receipt and server state), refused (with the server code) or expired. Offline, 401, 408, 425, 429 and 5xx failures retry with backoff and `Retry-After`, up to 25 attempts. Items from another owner or origin are refused. Logout and deletion purge the outbox and transient photos.

Android references are `PhotoProofTransport`, `AnonymousProofHttpClient`, `ContributionUploadHttpClient`, `PhotoCaptureHttpClient`, `FeedbackHttpClient` and `ForumHttpClient`. Acceptance needs staging runs for registration, binding, each write route, a refused write, an offline retry, evidence upload with expiry, owner history, sign-up, key recovery and a recovery email change with delivered codes, and Sign in with Apple, including re-authentication, on a provisioned device.

## B-BR-IOS-ANP / BUC-IOS-ANP — Official survey weeks

- The week list comes from the public ANP listing page. A week appears only when its block links both the weekly summary and the station detail spreadsheet. Weeks are ordered newest first.
- A download accepts only HTTPS `www.gov.br` URLs under the ANP price path, before the request and again after redirects. The listing is capped at 4 MiB and each spreadsheet at 64 MiB while it is read. A spreadsheet must have an `.xlsx` name, an accepted content type and a ZIP signature. Each ZIP entry must match its declared size and CRC-32, and inflation is capped while it runs.
- The summary must belong to the chosen week. Rows with an unknown product or state label are quarantined and counted, never guessed. Prices round half up to centavos, like Android `PriceAmount`, and are kept as integer milli-BRL. Station rows are kept only for the selected city's state.
- Each stored week keeps the SHA-256 and size of both source files and both row files in Application Support, excluded from backup. A row file that no longer matches its manifest drops the week.
- The active week is the chosen downloaded week, otherwise the newest download. Data is stale eight days after the survey end. A manual sync that finds no newer week records a verification. A station-detail failure keeps the summary as a partial week.
- On foreground, a check runs at most once every seven days without expensive or constrained networks. When the newest week is not current for the selected state, it is downloaded and made active.
- City history needs at least two downloaded weeks for the fuel. A price-drop alert compares the cheapest station of the city, otherwise the city minimum, with the previous downloaded week. It notifies once per fuel and week, and asks for notification permission only when the user turns an alert on.

Android references: `AnpListingScraper`, `AnpFileDownloader`, `StreamingXlsxParser`, `PriceTableBatchImporter`, `WeekPickerViewModel`, `HomeViewModel.refresh`, `SyncWorker`, `HistoryViewModel` and `EvaluatePriceDropAlertsUseCase`. Acceptance downloads two real weeks, restarts in airplane mode and compares the averages with the ANP files.

## B-BR-IOS-EV / BUC-IOS-EV — Admitted charging catalog and trip planning

- A refresh reads the national profile coverage and then every page of the same revision. The place and group counts must match the coverage, and the edition must be unchanged at the end. The OCM profile is used only when the national read fails. A failed refresh keeps the saved catalog. Private fields, foreign group owners and malformed rows refuse the page.
- Only admitted coordinates create map pins or route candidates. A place without coordinates stays in the list. Availability, opening hours and tariffs are unknown, never live or zero. A snapshot from another API origin is hidden, and a snapshot older than 24 hours is labelled stale.
- Filters follow Android `ChargingCompatibility.matches`. In the national catalog, a minimum power filter excludes groups with unknown power.
- The planner ports Android `EvEnergyModel`, `EvChargingPlanRules` and `PlanEvTripUseCase`. Road legs come from MapKit, and a failed leg is a missing route, never a straight line. Candidates are national places within the 25 km route corridor that offer the declared vehicle connector, with one connector per site. Private places are never stops. Each stop charges to the target, and a failed first stop is replanned from its arrival charge without energy from that site.

## B-BR-IOS-EMP / BUC-IOS-EMP — Abastevo Empresas driver operations

- Company access uses the account cookie plane as Android `CompanyAccessClient` does. A live personal session opens `POST /v1/org-access/session/login`, which must return the single `__Host-empresas-session` cookie (Secure, HttpOnly, SameSite=Strict, no Domain) and a CSRF token. The channel exists only in memory, is bound to the account and session family, and sends `Origin`, the cookie and `X-CSRF`. It lists and reads contexts, previews, accepts and declines invitations, and reads the applicable checklist. Context reads deny every 403/404 generically. An invitation needs the reviewed notice text, a code whose locator matches the receipt, and one operation id per decision, which a retry reuses.
- Entering a company needs an online server read of the membership, then device custody: signed `devices/check`, `devices/enroll` with label `iOS` when absent, and `devices/contact`. ACTIVE selects the company. LOCK keeps unsent work for delivery and accepts no new command. ERASE erases that partition alone. Generic refusals, outages and malformed answers never lock or erase. The selection is memory-only. Leaving or switching returns to the personal context. Records stay in the partition (account, origin, organization) that created them.
- The device reference, operation and attachment routes use `SignedRequestTransport` with the account proof inside the signed body. `/sync/reference` returns assigned assets, and with `trip_id` and no cursor it returns the open trip's driver-safe field projection. `/sync/operations` carries mission responses, trip commands, fueling, expenses and checklist runs. Receipt bytes go to the capability-bound `/documents/{id}/content/upload` ingress after an attachment session. The canonical enterprise JSON profile seals each operation with its payload digest. The app sends a null `run_clock` for trip start and finish and keeps company tracking off.
- The protected queue is a per-partition JSON file in Application Support, excluded from backup and file-protected on iOS. Commands retain creation order and dependencies. A batch holds up to 10 commands, and a mission response travels alone. Fueling history dismissed from the queue list stays in the partition and does not count toward the 500-command bound. Acknowledgements bind to the operation id and digest. Counted failures back off from 30 seconds up to 6 hours and respect `Retry-After`. A command pauses after 25 counted attempts and can be retried explicitly. A receipt attachment waits for its owning operation to be received and is refused locally if the owner operation was rejected. Final mission answer receipts remain available while the inbox needs them to establish state, and no Dismiss action is offered until then. Logout, account deletion and origin switch purge all partitions. Opening company mode with another account erases what earlier accounts left. A changed membership or a re-enrolled device drops the mission inbox and return checklist book bound to the earlier enrollment; queued commands stay.
- Refusals are shown as returned: sign-in, fresh authentication, invalid code, already a member, managed account, rate limit, entitlement, suspended membership or organization, revoked device and access denied. A refusal has no local effect on another organization or the personal context.

The shared canonical, operation, acknowledgement, reference-feed and attachment-session vectors cover the local and wire contracts. Staging and device acceptance follows the company journey above. Company review-result polling, managed unlock and Android's encrypted vault generations remain open. The iOS logout policy purges company data on the device.

## B-BR-IOS-EMP-TRIPS / BUC-IOS-EMP-TRIPS — Missions, trip transitions, fueling and return

- The selected company's mission inbox uses `POST /v1/orgs/{org_id}/missions/mine/list` with the account cookie, origin and CSRF proof. The protected copy belongs to the verified employee, membership and enrollment and states its age and first-page limit. The driver answers through signed `trip.mission.respond` at the mission revision. The app starts a confirmed mission with the assigned asset or an eligible choice and the mission soft reference. Offline answers and trip state stay in the authenticated company partition.
- Pause follows a running trip and resume follows a paused trip. Cancellation closes either state and requires a checked reason. The next expected revision is one plus the earlier lifecycle facts on this device. A start waits while the departure checklist run it names is still unsent on this device (Android EDR-352). A lifecycle step or finish waits while the step before it is unsent or paused on this device, and is released by any final receipt of that step (accepted, held for review or rejected) or its dismissal, as on Android; the server then answers `DEPENDENCY_PENDING` or holds a stale revision for review. Lifecycle commands and the finish name the start in `depends_on` until the start is accepted. When the start is rejected, its unsent lifecycle commands and finish become final locally with `START_REJECTED` and are never sent. Final lifecycle receipts can be dismissed; a refused or held start stays while its trip is kept. Local status and received outcome remain distinguishable. No transition contains a position, trace or run clock.
- Fueling uses the exact assigned asset, responsible employee, fuel, volume, amount, payer, payment method and optional discount rules. A receipt can be sent only through its owning operation, the existing attachment session and the issued upload capability. Once the company accepts the trip start, the open trip and fueling screens read the signed trip field projection, as Android `EnterpriseReferenceHttpClient` and `TripFieldWire` do, and show the driver's nearest authorization notice: product, maximum quantity, maximum amount, validity and stored or expired state. The read is memory-only and bound to the company session, enrollment and trip; a 404 means no field is listed. The response is refused whole when a voucher carries any other key, such as a code. Redemption stays with the partner station, and the driver UI cannot create or show a code. Route plan, document and maintenance counts from the same read are validated but not yet shown.
- The return checklist retains an applicable template and answers in the scoped company store. Required items, blocking outcomes and acknowledgment use the existing checklist rules. A finish can reference its accepted return run, or the driver can explicitly finish without a link. A required photo prevents checklist completion and is shown as unavailable because the run parser refuses photo evidence and the shared attachment ingress has no checklist-run target. All trip and checklist operations keep tracking off on iOS.

## B-BR-IOS-VEHICLE / BUC-IOS-VEHICLE — Vehicles, ledger records and ledger sync

- One new local vehicle is free, including guests. A second or third follows Android's `VehicleAdmissionRule`: `vehicles.multiple` from a server Premium status seen within 900 seconds, or a lease bounded by min(seen + 24 h, paid-through) for the same account and origin. The ceiling stays three. Held vehicles stay readable and removable, and removal keeps their records.
- A battery capacity is required for electric and plug-in hybrid vehicles. The decimal kWh input must resolve to a whole number of Wh between 1 and 1,000,000,000, inclusive. Comma and period are accepted decimal separators. Other propulsion types store no battery capacity.
- A record matches the backend refuel, expense or charge payload in exact units: centavos, milli-litres or milli-cubic-metres, Wh and metres. It has a stable lowercase UUID, the event instant and IANA zone, and a full, partial or unknown fill. The user selects a registered vehicle. Refuels need fuel propulsion; the fuel defaults to the vehicle's (LPG has none). Charges need electric propulsion. Inputs never round, and blank optional fields stay absent. Two local markers stay on the device because no route accepts them: an odometer reset or replacement, and a declared missed fill.
- Records from the first iOS ledger decode forward with nothing lost. The day is kept at local noon, the fill is unknown, an old expense becomes `other`, and a zero charge energy means not measured. Odometer-only readings stay local. Refuels take the vehicle fuel. Each migrated record needs owner review before upload, and its odometer counts as unverified (`odometer-unit-unverified`) until saved.
- Monthly indicators port `GetMonthlyIndicatorsUseCase`: half-open months in the device zone, full-to-full consumption and purchase cost per km, combined fuel-plus-charge cost over one shared distance, measured and reference Wh/km, and the change against the previous month. Undecidable results keep the frozen UNKNOWN reason. iOS also applies its segment marker (`odometer-segment-boundary`) and applies gaps and segments to the baseline month.
- Sync is per account and origin. The queue, acknowledged revisions, conflicts, tombstones, cursors and the lease are purged at logout and deletion. Opt-in sets server consent through `/v1/ledger/consent`. Commands go one at a time to `/v1/ledger/commands`, signed with the bound device key, with deterministic operation IDs (Java `nameUUIDFromBytes`) and the acknowledged revision. A 409 parks the record with base, current (read through `/v1/ledger/records`) and proposed versions. The owner keeps their version at the current revision, takes the server version, or decides later. A 403 pauses paid uploads, keeps local data and lets deletes through. 400 and 404 refuse without retry. Other failures retry with backoff and `Retry-After`.
- Deletes are free tombstones. A pull pages `/v1/ledger/records` with the opaque cursor, saving it per page and restarting on an expired one. It adds missing records and adopts newer revisions of records without local changes. It never resurrects a delete or overwrites pending work. Local CSV export and `/v1/ledger/erase` remain free. Erasure keeps local records on the device and clears their upload eligibility.

Android references are `VehicleAdmissionRule`, `BatteryCapacity`, `LedgerDraft`, `PremiumBounds`, `PremiumConsumption`, `PremiumEnergy`, `GetMonthlyIndicatorsUseCase`, `DispatchLedgerCommandUseCase` and `ResolveLedgerConflictUseCase`. ## B-BR-IOS-DRIVER / BUC-IOS-DRIVER — Driver shifts, distance and accounting

- Manual local shifts work signed out. Start requires one selected vehicle, a valid initial odometer and no other active shift for this owner and origin. Closing records the actual completion instant and validates the declared duration, distance basis and exact centavos. Legacy shifts belong to local guest history. Signing in does not transfer them.
- GPS distance needs explicit per-shift opt-in. The visible When-In-Use recording shares the location manager with active guidance and uses a separate lease. It can continue while locked and stops when the shift ends, permission is lost, the owner changes or the user stops GPS. Save an incomplete scoped checkpoint before starting; after a user stop, save only the derived whole metres and incomplete-coverage state. Interruption needs explicit review. Acknowledging the estimate selects it as the distance source for that shift. The estimate and odometer remain separate, and the driver HTTP routes leave the GPS estimate on the device.
- Hosted accounting is iOS-only. Before recording hosted earnings, the driver explicitly confirms the selected platform and either an inclusive net amount or a complete itemized money declaration. Local gross minus fuel does not establish net platform earnings. A selected local vehicle can be registered through existing cloud vehicle consent, device and command routes after explicit confirmation. Registration preserves an existing server record.
- The signed driver outbox durably freezes the command and reuses its operation ID, revision and epoch. A scoped lease prevents duplicate in-flight dispatch. Six attempts use the Android 5-second initial backoff and 15-minute cap, respecting `Retry-After`. A conflict parks for review. Logout, deletion and origin switch clear the queue and fence responses. Hosted writes use server Premium capability, while retained earnings and saved reports remain readable after lapse. Building a new report uses the server's paid report capability.

Android references: `DriverGpsLifecycle`, `DriverGpsService`, `DriverWorkViewModel`, `DriverWorkShiftTransition`, `DriverOutbox` and `DriverHttpCodec`. Accept only after a physical GPS shift, permission and restart tests, plus staging enrollment, signed accounting success, replay, conflict, lapse and owner isolation.
