Status: LOCAL_DONE / INTEGRATION_PENDING

## Delivered

- `backend/db/migrations/schema_min_supported` declares the oldest schema this
  build can run against (`000132`) and is embedded with the migration chain.
- `backend/internal/platform/migrate` now separates the compatibility rule from
  the database query. `Check` verifies that:
  - every known migration present in the database keeps its checksum;
  - no known migration up to the recorded maximum is missing;
  - the database is not older than `schema_min_supported`;
  - a newer database version is accepted as the additive side of the
    expand/contract window.
  Missing, modified or older-than-floor schemas still fail. Empty and malformed
  ledgers fail.
- The release workflow publishes `schema_min_supported` in
  `abastevo-release-manifest-v1` and validates both its format and
  `schema_min_supported <= migrations_max`.
- The Phase 2 dry-run agent validates the field when present, carries it into
  the plan receipt target/current payloads, and remains compatible with older
  manifests that predate the field. New manifests always carry it.
- Unit tests cover the compatibility matrix; the PostGIS integration test now
  proves a modified ledger fails and a newer additive version is accepted.

## Expand/contract rule recorded for the next microphase

A new release whose `schema_min_supported` is above the previous release's
floor contains a contract change. The apply-mode agent must refuse to run that
migration automatically while the previous image is still the rollback target;
additive releases keep the floor and may roll back. The field is now published
so the gate can be implemented without another schema change.

## Outstanding blockers for the rollout executor

- The plan's Phase 3 rollout wording (`maxSurge`, `namespace quota`,
  `rollout undo`) is Kubernetes-specific, while the repository's staging
  artifacts are Docker Compose (`infra/compose.staging.yml`,
  `infra/scripts/deploy.sh`, `infra/scripts/backup.sh`). There is no live
  staging cluster in this workspace. Implementing either path without an owner
  decision would invent infrastructure.
- The landing archive is currently a GitHub Actions artifact. The Phase 3 agent
  needs an anonymous distribution path; the natural option is to add
  `landing-dist.tar.gz` to the signed OCI release artifact.
- Actual two-consecutive-merge acceptance and the broken-image rollback drill
  require the staging host/cluster and remain OWED.
