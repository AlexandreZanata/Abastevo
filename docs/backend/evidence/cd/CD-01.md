## Delivered

- `.github/workflows/release-staging.yml` builds and publishes `api`, `worker`
  and `migrate` from `infra/docker/Dockerfile` with `REVISION=<sha>` to
  `ghcr.io/<owner>/abastevo-<role>:sha-<sha>`. It also builds the landing for
  `https://teste.abastevo.com.br` and uploads `landing-dist.tar.gz`.
- Each image gets an SPDX JSON SBOM and a build-provenance attestation bound to
  its digest. The workflow records image references and digests.
- `release-manifest.json` (schema `abastevo-release-manifest-v1`) contains the
  commit SHA, creation time, one `image@digest` per role, landing bundle
  SHA-256, highest migration version and the triggering workflow-run URL. It is
  signed keyless with cosign and published as a workflow artifact and as the
  OCI artifact `ghcr.io/<owner>/abastevo-release:sha-<sha>` plus `staging`.
  `schema_min_supported` is deferred to Phase 3, where the runtime schema
  contract is introduced; publishing a placeholder would misstate compatibility.
- The final workflow step prints the exact `cosign verify-blob` command with
  the workflow certificate identity at `refs/heads/main` and the GitHub OIDC
  issuer.
- `scripts/check-release-workflow.sh` rejects unpinned actions,
  `pull_request_target`, `pull_request`, non-`GITHUB_TOKEN` secrets, `set -x`,
  environment dumps, echo of variables and `latest` tags. It runs from Quick.
- `.github/CODEOWNERS` explicitly assigns `.github/workflows/` and
  `infra/deploy/` to the owner. The default owner entry remains.
- `backend.yml` path selection includes the release workflow and the guard so
  the backend gate runs when this pipeline changes.

## Release gate semantics

- Automatic runs listen to completed `quick`, `CI` and `backend` runs on
  `main`. The gate requires a successful `push` run for all three workflows
  for the same `head_sha` before any build job starts.
- Optional path-filtered workflows that did not run for a commit leave the
  release gate closed with no artifact; the gate does not fabricate success.
  A run that exists but is not successful closes the gate with an error.
- Manual dispatch requires `refs/heads/main` and a full 40-hex SHA that is an
  ancestor of the checked-out `main`; it does not use an environment or a
  secret.
- Minimal permissions are declared per job: read-only by default, with
  `packages: write`, `id-token: write` and `attestations: write` only where
  image publication/signing/attestation needs them. `actions: read` is limited
  to the gate query. No secret beyond the automatic `GITHUB_TOKEN` is used.

## Known constraints recorded before merge

- Branch protection currently requires only `Quick verification`. `CI` and
  `backend` are path-selected workflow signals, not protection-required
  checks. The release gate requires all three when they run; a commit that
  does not trigger one of them does not produce a release.
- CODEOWNERS is present, but the repository setting `require_code_owner_reviews`
  is false. Enforcing owner approval is a repository-settings decision outside
  this change.
- GHCR package visibility is not changed by the workflow. Anonymous pulls and
  `gh attestation verify` for the published artifacts are verified after the
  first real `main` run; a package still private is reported, not worked around
  with a personal token.
