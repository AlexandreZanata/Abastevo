## R2 — captured staging source of truth

`infra/k8s/staging/` captures the live `abastevo-temp` API/web Deployments,
Services, DB StatefulSet, ResourceQuota, registry-sync CronJob and Caddy
ConfigMap. Images, host paths, cluster IPs, NodePorts and dynamic metadata are
placeholders rendered only from an operator file outside Git; secrets use
`secretRef`/`configMapRef` only. The pre-existing DB PVC is referenced but not
templated.

`render.py` substitutes only declared `${NAME}` placeholders, leaving pod shell
variables such as `$POSTGRES_USER` intact. `normalize-diff.py` is the
`KUBECTL_EXTERNAL_DIFF` helper for the proof; it ignores only server-managed
metadata and client-apply bookkeeping (creation timestamp, generation, resource
version, UID, managed fields, status, last-applied annotation, deployment
revision, manual restart annotation). Spec, labels, desired annotations, data
and pull policies are compared.

Proof: the rendered namespace was compared with `kubectl diff -n abastevo-temp`
through the normalizer and exited **0 with empty output**. Raw `kubectl diff`
reported only the ignored server-managed fields. No object was applied.

## R7 — landing in the signed OCI artifact

The release workflow adds `landing-dist.tar.gz` as an
`application/vnd.abastevo.landing.tar+gzip` layer, verifies its digest against
the signed manifest before push, and checks the published layer after push.
The agent verifies the OCI layer digest, the archive SHA-256 and the manifest
`landing_sha256` before extraction. The dry-run harness now carries the landing
layer in its OCI fixture.

## R8 — least-privilege RBAC and kubeconfig

`infra/k8s/staging/rbac/deploy-agent-rbac.yaml` defines a ServiceAccount, Role and
RoleBinding restricted to `abastevo-temp`: deployments get/list/watch/patch,
replicasets get/list/watch, jobs create/get/list/watch/delete, pods
get/list/watch, pods/log get and resourcequotas get/list. No secrets,
ConfigMaps, Services, pods/exec, other namespaces or cluster-scoped resources.
It is **not applied** in this delivery; client-side dry-run validation passed.

`infra/deploy/agent/kubeconfig-from-serviceaccount.sh` creates the kubeconfig
after the RBAC is applied. The token is read from `kubectl create token`
through stdin, never printed, never placed in argv, and written only to the
mode-600 output file. A stubbed run proved the token does not appear in stdout
or stderr and the file mode is 600.

## R3–R6 — apply mode

The agent keeps the dry-run verification/plan and adds an opt-in
`ABASTEVO_APPLY=1` path. The k8s adapter is isolated in
`infra/deploy/agent/runtime/k8s.sh`; orchestration lives in
`infra/deploy/agent/apply.sh`. Release order:

1. schema-floor gate (current state or live annotation; database query Job;
   contract floor refused);
2. verified `pg_dump` backup Job with `pg_restore --list`, SHA-256 and
   retention 7;
3. migration Job from the signed migrate digest (`backoffLimit: 0`,
   `ttlSecondsAfterFinished: 86400`);
4. one shared `kubectl set image` for the api and worker containers, pull
   policy `IfNotPresent`, `rollout status --timeout`;
5. smoke: `/health/ready`, `/`, `/consultar/`, one station-list read, portal
   manifest and one search shard;
6. landing extraction to `releases/<sha>`, relative `current` symlink, retain
   the previous release and the last 5;
7. `current.json` written atomically last, then a mode-600
   `abastevo-deploy-receipt-v1` receipt.

Any failure after the image update runs `rollout undo` for both containers; a
switched landing is restored; failures before the image update write a failure
receipt and leave the deployment untouched. Migrations are never rolled back.
The agent takes an internal `apply.lock` in addition to the service `flock`.

Surge is opt-in: `ABASTEVO_ALLOW_SURGE=1` and quota headroom at least
`ABASTEVO_SURGE_CPU_MILLI` produce `maxSurge: 1` / `maxUnavailable: 0`;
otherwise the safe `0/1` strategy is used and the receipt records the measured
gap. The R5 worker-overlap proof is still OWED, so the shipped default is no
surge. The current live quota headroom is 2.5 CPU, but that alone does not
authorize surge.
