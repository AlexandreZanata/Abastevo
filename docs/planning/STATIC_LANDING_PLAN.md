## Product rules before behavior

- **B-BR-L01 — Truthful product presentation:** use the approved lowercase abastevo name and existing [brand](../brand/IDENTITY.md). Describe demonstrated features with their limitations. Community observations and dated ANP references remain distinct; never imply ANP affiliation, guaranteed current prices, coverage everywhere, automatic trusted publication, guaranteed savings or production certification. Label future capability explicitly.
- **B-BR-L02 — Restrained navigation:** present one clear product explanation and ordinary links. No urgency/countdown, popup, signup wall, notification request, autoplay, repeated purchase/download banners or sticky conversion bar. A visitor can understand the project without taking an action.
- **B-BR-L03 — Honest store state:** before a verified public listing, show plain text “Em breve na Google Play”; no disabled/fake download link, invented release date or unofficial APK fallback. After the maintainer supplies the public listing, verify its app/package identity and replace the notice with one normal “Ver na Google Play” link or the official badge (single placement). Preserve `com.anpfuel`; do not derive or publish an unverified store URL from the package alone.
- **B-BR-L04 — Essential content is static:** product copy, headings, GitHub/store links, legal/help destinations and SEO metadata exist in delivered HTML. With JavaScript disabled or failing, the page remains usable and links still work. TypeScript only enhances optional interactions; it does not fetch or inject essential content.
- **B-BR-L05 — Evidence-based SEO:** publish accurate visible content and consistent metadata. Never copy another organization's identity, rating, review count, testimonials, social profiles or availability. Structured data cannot contain unverified facts. SEO acceptance means a technically prepared site, not a promised Google position or indexation date.
- **B-BR-L06 — Minimal data surface:** no cookies, third-party trackers, remote font calls, location collection or visitor accounts in this phase. Any privacy/help text describes actual behavior and links to maintained project material; do not present a draft policy as legally approved. Hosting access logs are reviewed when hosting is selected.
- **B-BR-L07 — Required public legal and help destinations:** the site publishes, as static pages reachable from the footer, a privacy page (`/privacidade/`), an account/data deletion request page (`/excluir-conta/`), community terms (`/termos/`) and the contact channel from D-L04. Content is derived from the maintained [security/privacy plan](../security/SECURITY_PRIVACY.md), [location/media policy](../security/LOCAL_MEDIA_LOCATION_POLICY.md), [free account access](../security/FREE_ACCOUNT_ACCESS.md) and [community moderation](../product/COMMUNITY_MODERATION.md); it states the actual current behavior, retention and rights workflow and marks not-yet-shipped features as such. The wording difference between the README/media policy (all photo copies within 24 hours) and the older 14-day sanitized-evidence line is resolved in the [T01 contract](../product/LANDING_CONTENT_CONTRACT.md#legal-pages-b-br-l07): the media policy supersedes it, and public wording is labelled as project policy until release evidence exists. A Google Play listing for an app with accounts and user-generated content is expected to need a privacy-policy URL, a web deletion destination and a data-safety declaration; T01 verifies the **current** Play Console policy text, records source and date, and repeats the check at listing time. The plan does not assert current policy wording. Pages are not presented as legally approved.

Use cases:

- **BUC-L01:** a visitor opens `/`, understands what abastevo does, reads how community and ANP sources differ, and finds the project links without registering or granting permissions.
- **BUC-L02:** a visitor opens the confirmed GitHub repository from an ordinary HTML link, using keyboard or touch, with JavaScript enabled or disabled.
- **BUC-L03:** a visitor sees the honest prelaunch notice; after an authorized listing update, the same section leads to the verified public Play Store app. Missing/invalid configuration keeps the prelaunch state; it never produces an empty or unsafe link.
- **BUC-L04:** a crawler or link-preview client receives the page copy, canonical URL, description, social metadata and factual JSON-LD in the initial HTML response, without executing JavaScript.
- **BUC-L05:** a visitor or store reviewer opens privacy, deletion and terms pages from the footer without JavaScript, reads the current behavior in plain language and finds the contact channel.

4. “Como funciona”: three short steps for consulting available information, checking source/date/condition, and contributing through the app when available. These are explanations, not functional website widgets.
5. “Para quem é” (include only if copy is verified): three short profiles such as private driver, ride-app driver and small fleet operator. Factual wording, no savings promise (B-BR-L01).
6. “O projeto”: transparent source distinction, free community participation, a link to source code and a “Privacidade em resumo” block of short statements matched to the legal pages (browsing without account or GPS, limited photo retention as stated by the reconciled policy, no trackers on this website, open source). 7. “Aplicativo”, “Acompanhe o projeto” and brief questions: Android/store state, project status, source/freshness and contribution basics. Following the project needs no signup: ordinary links to the repository, its releases page and the repository releases Atom feed (verify the feed URL for the confirmed repository). The page collects no email. Native `<details>` is sufficient for optional FAQ disclosure; no FAQ rich-result promise. FAQ questions follow real search intent where the product supports the answer, for example how to find a station's fuel price, what the ANP weekly survey is, the difference between a community observation and an ANP reference, and (only if the app's calculator behaves as described) how to compare ethanol and gasoline. Answers cite official sources where used and never promise “cheapest near me”.
8. Quiet footer: GitHub, privacy, account deletion, terms, contact, source attribution (ANP data with a link to the official source), “Código aberto sob licença MIT”, “Não afiliado à ANP”, and trademark references ([TRADEMARKS](../../TRADEMARKS.md)).   package-lock.json
  scripts/build.mjs
  scripts/check.mjs
  tests/...
  README.md
  dist/                 # ignored generated deploy artifact

Use ordinary handwritten HTML/CSS and browser DOM APIs. Compile TS locally to an ES module loaded with `type="module"`; JSON-LD uses its own static `application/ld+json` script. No React, Astro, Svelte, Tailwind, component framework, runtime library or bundler is needed. Node/npm is build/check tooling only; the published site is files served by any suitable static host. Do not import the reference repository's admin server, framework or deployment configuration.

TypeScript **7.0.2** is confirmed by the maintainer and its [official release](https://github.com/microsoft/TypeScript/releases/tag/v7.0.2) was verified on 2026-10-05. At P25-T02, verify the actual registry package/artifact, binary name, supported `tsconfig` options and defaults (they may differ from 5.x examples), pin the exact version without a range, commit the lockfile, select and record a supported Node version, and prove compiler output. Record dependency need, MIT license and scoped security review; no dependency is installed by this plan. If the exact version is unavailable in the execution environment, record the failure and resolve it before accepting T02; do not silently substitute a version.

Compiler settings: strict typing, DOM types, explicit module/target selection for the frozen browser support, `noEmitOnError`, root `src/` and generated output under `dist/assets/`. A minimal build copies authored static files and compiles TS; any necessary host-specific URL substitution happens at build time with missing/invalid-value checks. Essential HTML is never client-rendered. `dist/` contains no TS sources, server code, private configuration or source maps by default; building twice from the same inputs yields the same artifact. Set store state in authored/build-time static content and verify every affected visible/metadata location together. **The build fingerprints CSS, JS and image file names with a content hash and rewrites references**, so long-lived immutable caching is safe while HTML stays short-lived.

**Use of TypeScript.** TypeScript is a requirement of the stack, and every use must remain an optional enhancement. Candidate interactions, each independently testable and harmless without JS: highlight the active in-page section in the header (`IntersectionObserver`, respecting reduced motion); a “copy repository link” helper with a plain-link fallback; an unobtrusive “back to top”. Select only those the approved wireframe needs. Build/check scripts may also be authored in TypeScript and compiled by the same toolchain if that keeps the toolchain single.

GitHub destination: `https://github.com/AlexandreZanata/abastevo` (D-L01 resolved; the previous repository name redirects to it). Open links in the same tab by default; if a new tab is chosen, communicate that behavior and use `rel="noopener noreferrer"`. Store URL, final domain and hosting provider are pending owner inputs (D-L02, D-L03, D-L08), required only for their respective activation/publication steps. Existing test/staging endpoints are not assumed to be the landing's canonical address.

### Hosting and response policy

The plan is host-neutral at the artifact level but the host determines what the site can enforce. Selection criteria, to be recorded in T01 and verified against each provider's current documentation at selection time (not asserted here): custom response headers (security headers, `X-Robots-Tag` for previews, per-path cache), redirects (HTTP→HTTPS, `www`→apex, trailing-slash policy), a real 404 status, automatic HTTPS, preview deployments, access-log/privacy posture, cost/limits and rollback to a previous immutable artifact.

| Option | Direction |
|---|---|
| Static-site hosts with file-based `_headers`/`_redirects` style configuration (for example Cloudflare Pages or Netlify) | Preferred direction: meets the criteria without running a server. Verify the configuration syntax and limits at selection. |
| GitHub Pages | Simple and free, but custom response headers are not configurable as far as known; if chosen, verify the limitation and compensate with in-document metadata only, accepting weaker header coverage. |
| Self-managed server (Caddy, as in the reference) | Maximum control, ongoing maintenance and operations cost; only on explicit maintainer choice. |

Header baseline for the chosen host (adapted from the reference's `_headers`, without copying its project-specific rules): `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`; `Permissions-Policy` denying camera, microphone and geolocation (the site uses none); a strict `Content-Security-Policy` with `default-src 'self'` and no inline executable script (an `application/ld+json` block is data, not executed script); `Strict-Transport-Security` only after stable HTTPS is verified, with `preload` omitted unless consciously decided because it is hard to reverse; long immutable cache for fingerprinted assets and short revalidated cache for HTML. Preview deployments send `noindex` through the host or the HTML.
